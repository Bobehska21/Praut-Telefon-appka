# Focus Mode

A calm app that helps you concentrate. When focus mode is on, only the apps you allowed in advance
(a whitelist) stay available; everything else is hidden or blocked until you turn the mode off.
No account, no backend, no ads: all data stays on the phone.

- React Native + TypeScript on Expo SDK 58 (**development build, not Expo Go**)
- Native module `Focus`: Kotlin on Android, Swift on iOS (`modules/focus`)
- State: Zustand persisted in MMKV. Czech UI, English included (`src/i18n`).

## Status

| Part | State |
|---|---|
| Shared TypeScript (store, scheduler, unlock guard, stats, UI) | done, unit-tested (`npm test`) |
| Android native module | compiles and passes Android lint; **not yet run on a device** |
| iOS native module and 3 extensions | written; `expo prebuild` generates the Xcode project with all targets; Swift syntax-checked and the pure logic unit-tested on macOS; **never compiled against the iOS SDK or run** (no Xcode was available) |

Read "Known limitations" before relying on it.

## Requirements

- Node 22.13+ (tested with 26), npm
- Android: JDK 17, Android SDK platform 36 + build-tools 36, a physical device (API 24+)
- iOS: macOS with Xcode 16+, CocoaPods, a **paid** Apple Developer account, a physical device (iOS 16.4+)

## Build and run

```sh
cd mobile
npm install
npm run typecheck && npm run lint && npm test   # JS checks, no device needed
npm run android                                  # builds a development client and runs it
npm run ios                                      # needs the setup in "iOS" below
```

The native folders `android/` and `ios/` are generated by `expo prebuild` and are git-ignored.
Change native behaviour in `modules/focus/` and `targets/`, never in the generated folders.

Before the first real build replace the placeholder identifiers in `app.json`:
`ios.bundleIdentifier`, `android.package` (both `com.example.focusmode` now) and the App Group
`group.com.example.focusmode` (see "iOS").

## Architecture

```
src/modules/focus/     TypeScript contract (FocusModuleApi) + per-platform adapters
modules/focus/android/ Kotlin: launcher, foreground service, overlay, receivers, permissions
modules/focus/ios/     Swift: Expo module, shared logic
targets/               iOS app extensions (shield UI/actions, schedule monitor)
src/features/          scheduler, unlock guard, stats (pure logic, unit-tested)
src/store/             Zustand + MMKV
src/app/               expo-router screens
```

The native side is the source of truth for "is focus mode running" (it survives the app being
killed and a reboot). The JS store mirrors it through `syncWithNative()` on start and whenever the
app returns to the foreground, and keeps history for the statistics.

Platform differences are shown openly in the UI: on iOS there is no app grid and no list of
installed apps (Apple only exposes opaque tokens through a system picker).

## Android

### How it works

- **Focus grid:** the app does not need to be your default home app. Starting focus mode opens a
  grid of the allowed apps (plus phone and messages) with a Stop button. If you press Home or open
  Recents, the regular launcher counts as a non-allowed app and the grid is shown again right away.
  Android cannot set a default launcher silently, so you may *optionally* choose this app as home
  in system settings; it then shows all apps while focus mode is off.
- **Blocking:** a foreground service polls `UsageStatsManager` (~0.7 s). If the app in front is not
  allowed, a full-screen overlay (`SYSTEM_ALERT_WINDOW`) says
  "Tato aplikace je v režimu soustředění vypnutá" with a Back button that returns to the launcher.
- **Persistence:** persistent notification, `START_STICKY`, `BOOT_COMPLETED` receiver and an alarm
  for timers and schedules.
- **Always allowed:** default dialer and SMS app, emergency/phone packages, keyboards, system UI and
  permission dialogs.

### Permissions (and why)

| Permission | Why | How it is granted |
|---|---|---|
| Usage access (`PACKAGE_USAGE_STATS`) | know which app is in front | Settings screen |
| Display over other apps (`SYSTEM_ALERT_WINDOW`) | show the block screen over a blocked app | Settings screen |
| Notifications (`POST_NOTIFICATIONS`) | Android requires a notification for a foreground service | runtime prompt |
| Foreground service, special use | keep focus mode alive | manifest |
| Receive boot completed | resume after reboot | manifest |
| Exact alarms (`SCHEDULE_EXACT_ALARM`) | start schedules on time (Android 14+ needs the user to allow it) | Settings screen |
| Battery optimization exemption | stop the system from killing the service | Settings screen |
| Accessibility service (optional) | more reliable detection of the opened app | Settings screen, off by default |

`QUERY_ALL_PACKAGES` is deliberately **not** used (Google Play restricts it); package visibility is
declared with `<queries>`.

### Optional AccessibilityService and Google Play

`FocusAccessibilityService` is declared in `modules/focus/android/src/main/AndroidManifest.xml` but
does nothing until the user enables it in system Accessibility settings. It only reads the package
name of the window that came to the front (`canRetrieveWindowContent="false"`).

Declaring any AccessibilityService makes Google Play review the app's accessibility use. For a Play
build that must avoid it, delete the `<service ... FocusAccessibilityService>` element from that
manifest (and the "Extended blocking" switch in Settings has no effect). The UsageStats + overlay
path works without it.

### Google Play declarations to prepare

`PACKAGE_USAGE_STATS`, `SYSTEM_ALERT_WINDOW`, and a foreground service of type `specialUse` each need
a justification in Play Console. The text used for `specialUse` is in the manifest `<property>`.

### Testing on a real device

1. `npm run android` with a device connected (USB debugging on).
2. Go through onboarding and grant every permission. Most are granted on a system settings screen;
   come back to the app after each.
3. Make a profile with 2-3 allowed apps, start a 25-minute session.
4. Open an allowed app: it works. Open any other app: the block screen appears and the attempt
   shows in Statistics.
5. Kill the app from recents, reboot, set a schedule: focus mode must come back / start by itself.

## iOS

### How it works

iOS has no equivalent of a custom launcher or of reading the foreground app. Blocking uses Apple's
Screen Time API (`FamilyControls`, `ManagedSettings`, `DeviceActivity`):

- **Authorization:** `AuthorizationCenter.requestAuthorization(for: .individual)` (the user confirms
  with Face ID / passcode).
- **Choosing apps:** `FamilyActivityPicker` in a system sheet. The result is opaque tokens, so the
  app never sees names or a list of installed apps. The selection is stored per profile in an App Group.
- **Whitelist mode:** `shield.applicationCategories = .all(except: allowedTokens)` on a named
  `ManagedSettingsStore("focus")`. Everything not chosen shows the shield.
- **Shield screen:** `shield-config` extension (text "Tato aplikace je v režimu soustředění vypnutá",
  Back button); `shield-action` extension closes the blocked app.
- **Timers and schedules while the app is closed:** `device-activity-monitor` extension. A timer of
  15+ minutes registers a one-shot interval that lowers the shield; each enabled schedule registers a
  daily interval and the extension filters by weekday. App and extensions share state through the
  App Group (`FocusShared.swift`).
- **No app grid:** the home-screen grid of allowed apps does not exist on iOS; the UI says so.

### Setup (needs a paid Apple Developer account)

1. Put your Team ID in `app.json`: `expo.ios.appleTeamId`. Replace `com.example.focusmode` (bundle id
   and the App Group `group.com.example.focusmode`, which must be `group.<bundle id>`).
2. **Request the Family Controls entitlement from Apple.** Without it the capability cannot be used
   on a device with a distribution profile:
   - Sign in at developer.apple.com and open the Family Controls (Distribution) request form
     (search "Family Controls entitlement request" in Apple's developer documentation).
   - Request it for **each of the four bundle ids**: the app (`<bundle id>`) and the extensions
     `<bundle id>.device-activity-monitor`, `<bundle id>.shield-config`, `<bundle id>.shield-action`.
   - Describe the use: a personal focus tool that restricts apps chosen by the user on their own
     device (`.individual` authorization), no data leaves the device.
   - Approval can take days to weeks. Until then the development entitlement lets you run on your own
     registered devices (a free "Personal Team" cannot use Family Controls at all).
3. Register the App ID capabilities **Family Controls** and **App Groups** for all four ids (EAS or
   Xcode "Signing & Capabilities" does this automatically once the entitlements are approved).
4. `npx expo prebuild -p ios`, then `cd ios && pod install`, open in Xcode, pick your team, run on a
   **physical device** (iOS 16.4+). The Screen Time API does not work reliably in the simulator.

### Testing on a real device

1. Run the app, grant Screen Time access in onboarding.
2. Create a profile, tap "Choose apps in system picker", select 2-3 apps, Done.
3. Start a 25-minute session. Allowed apps open; everything else shows the shield with the Czech text.
4. Lock the phone and wait for the timer: the shield must lift by itself.
5. Add a schedule (15+ minutes) a few minutes in the future and confirm it starts with the app closed.

## Known limitations

### Both platforms
- The impulse guard (30 s countdown, sentence) protects only the in-app stop button. A determined user
  can still uninstall the app, revoke permissions, or reboot into safe mode. It is a nudge, not parental control.
- Stats count attempts, not time spent trying; the exact count depends on how the platform reports them.
- Custom timers shorter than 15 minutes work in-app on iOS but end only the next time the app reads
  its status (the system will not monitor shorter intervals).

### Android
- **Never run on a device.** The Kotlin module compiles and passes Android lint, nothing more.
- Detection polls UsageStats every ~0.7 s, so a blocked app is visible for a moment before the overlay.
- The overlay needs "Display over other apps"; without it blocking cannot show the block screen.
- Android 12+ may refuse to start the foreground service from the background (scheduled start while the
  app is closed) unless the user allowed exact alarms or the device just booted.
- Other launchers' "Home" is treated as a blocked app; the user returns to the focus grid with Back.
- OEM battery managers (Xiaomi, Huawei, Samsung "sleeping apps") can kill the service even with the
  exemption; the alarm and boot receivers restore it on the next event.
- Google Play needs justifications for usage access, overlay and `specialUse` foreground service
  (and review of the optional AccessibilityService, see above).

### iOS
- **Never compiled or run.** Written against Apple's documented signatures, not built with Xcode.
- Requires a paid Developer account and Apple's Family Controls approval (can take weeks).
- Apps are opaque: no names or icons outside Apple's picker, no app grid, and the in-app blocked
  screen cannot name the app.
- In whitelist mode only individually chosen **apps** (and web domains) are honored. If the user
  picks a whole category in the system picker, its apps are NOT allowed by `.all(except:)`.
- Reports from developers say `.all(except:)` exceptions can be unreliable, and that Phone and
  emergency calling cannot be shielded while Messages can; none of this is confirmed by Apple's
  documentation. Verify on a device that Phone and Messages stay reachable.
- DeviceActivity needs intervals of at least 15 minutes, callbacks are not guaranteed while the
  device is idle, and the shield screen follows the **device** language (extensions cannot read the
  in-app language setting). A schedule that crosses midnight is assumed to work as a wrapping interval
  but is unverified.
- Blocked-attempt counting is approximate: the system may draw the shield more than once per attempt
  (repeats within 3 s count once) and does not report attempts to the app.
- At most 19 schedules are monitored (system limit of 20 activities, one reserved for the timer).
- `@bacons/apple-targets` 5.x was installed against Expo SDK 58 and `expo prebuild` works, but the
  Xcode project it generates was not opened or built.
